# FCJ archive — problems list

Started 2026-11-13. Findings from offline audit of `fcj-static/` + `fcj-crawl/`,
before browsing. Nothing in `fcj-static/`, `fcj-crawl/` or `fcj-kit/` was modified.

## P1 — Five papers unreachable by configuration (not lost)

`fcj-redirects.conf:419` holds seven rules back with 503 on the stated reason
"spam injected into the only copy". **That premise is false.** All five articles
have a clean copy on their issue subdomain, verified by diffing external link
domains between the apex copy and the twin:

| article | spam in apex copy | clean twin on disk |
|---|---|---|
| FCJ-004 | `instantcasino.io` | `one…/fcj-004-….html` |
| FCJ-138 | `onlinecasinomaxi.de` | `twenty…/2012/06/18/fcj-138-…/` |
| FCJ-198 | `bestecasinozondercruks.com`, `safecasinosnotongamstop.com` | `twentyseven…/2016/03/08/…` |
| FCJ-199 | `bestwallet.com`, `exhalewell.com`, `pokerscout.com` | `twentyseven…/2016/03/18/…` |
| FCJ-202 | `sambaslots.org` | `twentyseven…/2016/03/21/…` |

The 503s therefore make five papers unreachable when they could be 301s to clean
copies, exactly like the other 207 redirects. This is the only thing in the
archive that currently loses papers, and it is a config decision, not data loss.

**Fix:** replace the seven 503 rules with 301s to the issue-subdomain copies.
No text restore needed — the clean text is already in `fcj-static/`.

Secondary: the comment names a "Dec 2021 dump" as the restore source. No such
file is evident; `fcj-kit/` holds `fcj2022.sql.gz`. Worth reconciling the note.

## P9 — FCJ-129 was about to be lost, and nothing had noticed

Found 2026-11-13 by the first run of `build/inventory.py`, which reported 226 of
228 numbers rather than the expected 227.

**FCJ-129 "Ubiquity Editorial (Cont.) – Interaction Designs for Ubicomp
Cultures"** (14,009 words, issue 19) exists in exactly one place:
`fibreculturejournal.org/fcj-129-interaction-designs-for-ubicomp-cultures-3/`.
Note the `-3` — a WordPress collision suffix.

- Issue 19's root links it as `/fcj-129-interaction-designs-for-ubicomp-cultures/`,
  without the suffix, so the link is dead on the live site.
- No copy exists on `nineteen.fibreculturejournal.org`.
- **`fcj-redirects.conf` has no rule mentioning it**, so the apex copy is not
  reachable through any redirect either.
- Its only copy is on the apex host, where all the P3 contamination is. Checked
  by hand: clean. The one unexpected external domain, `themasterplan.in`, is the
  theme designer's credit link and appears in 2,253 of the mirror's 2,278 HTML
  files.

Recovered by `inventory.resolve_with_apex`, which retries a failed link with
WordPress collision suffixes `-2`…`-5` on the issue host and then the apex, and
flags the result in `Manifest.apex_sourced` so the spam audit must cover it.
Regression test: `test_fcj_129_is_recovered_from_the_apex_collision_suffix`.

**Why the earlier audit missed it:** that audit asked whether each FCJ number
appeared anywhere in the mirror, and FCJ-129 does appear — in eight files,
mostly category listings and author archives. Presence is not reachability. The
link-driven inventory asks the question that matters, which is whether a reader
following the journal's own links arrives at the paper.

## P3 — Spam-contaminated duplicates ship in the archive

The WordPress site was compromised at some point: 145 HTML files carry injected
links to 88 junk domains (casinos, crypto, CBD, sweepstakes). Injection is inline
in body text, e.g. `…platforms like an <a href="instantcasino.com">instant play
casino</a> are designed to…`.

**All 145 are on the apex host. Zero on any of the 32 issue subdomains.** The
served copies are clean, and 66 of the affected apex article copies are shadowed
by 301s. But the files still ship in the 620 MB, and the set includes
`index.html?p=NNNN.html` query-string duplicates that no redirect covers.

**Fix:** drop the contaminated apex duplicates from the archive before publishing.

### RESOLVED 2026-11-14 — the domain list is now generated, not hand-written

`fcjarchive/build/audit_spam.py` discovers the injected domains by evidence
and writes `fcjarchive/data/spam-domains.txt`. The method is the one that found
the contamination in the first place, made repeatable: **diff an article against
itself**. The mirror holds most papers twice, so a domain in the apex copy that
is absent from the same paper's clean issue-subdomain twin was put there by
someone who was not the author.

Measured over 190 article pairs: **78 injected domains across 54 apex files.**

The list reads unambiguously as **paid link insertion**, not crude spam: 12
casino domains, 8 crypto, several CBD and cannabis, plus car transport, skip
hire, urgent care, payday loans, a katana shop and two SEO agencies. Many are
real businesses. That is the business model — the links were sold.

**A false positive was caught and is worth recording.** `chcf.org`, the
California Health Care Foundation, was flagged as injected into FCJ-144, a
paper on GE's "healthymagination". It is a real citation: the author printed
the URL as plain text in their reference list, and only the apex copy has it as
a link. A guard reading `href` attributes alone sees "present in the apex,
absent from the twin" and accuses a source the paper genuinely cites. The guard
now tests whether the domain appears **anywhere in the clean text**, linked or
not, and `chcf.org` is recorded in the output as considered-and-rejected with
its reason.

**Invariant 1 holds:** zero of the 78 domains appear anywhere in `content/` or
in `site/`. Asserted by `tests/test_audit_spam.py` over both trees.

**Still unverifiable: 198 domains on 61 apex-only pages** — category listings,
calls for papers and other pages with no clean twin to diff against. The
twin-diff cannot reach them. None are published by the archive, so they are
reported rather than enforced; if an apex-only page is ever published, it needs
checking by hand first.

## P4 — Editorial intros: the issue root IS the editorial (mostly)

Mat's design intent: the editorial should open at each subdomain root. Tested by
measuring body prose at all 31 issue roots. **Confirmed for 25 of 31** (1,200–6,500
words of editorial prose plus links to that issue's papers).

**Exceptions — root is a landing page, not an editorial:** issues 1, 2, 5, 23 and
mesh. Their word counts (700–1,195) are mostly nav furniture around a theme title
(`// Issue 5 2005: Precarious Labour`) and an article list. Editorial either lives
elsewhere on those hosts or was never published. Needs Mat's editorial knowledge.

**Duplicate editorials:** on issues 8, 11, 18 and 19 the standalone editorial page
(`issue-08-editorial`, `issue-18-trans`, `issue-1-ubiquity` — note the last is
issue 1's name on the issue 19 host) contains the same text as the issue root.
Keep one canonical copy.

**Two anomalies — both RESOLVED 2026-11-13:**
- Issue 16: `games-of-multitude` is **FCJ-113**, a paper. Its `<title>` carries
  the citation even though its URL carries no number — issue 16 numbers nothing
  in its slugs. Not an anomaly, just the convention. A duplicate-editorial test
  based on word-count proximity would have discarded it, so it is now a
  regression test: `test_issue_16_games_of_multitude_is_a_paper_not_a_duplicate`.
- Issue 12: the probe mismatch was the measurement, not the content. The issue
  root holds the editorial **plus** a hand-written list of the issue's papers,
  so root and standalone page are never byte-identical. The archive takes the
  standalone page and generates the contents list itself.

**Design consequence:** in the new archive, make this uniform — `/issues/NN/`
serves the editorial and links the issue's papers, which is what the subdomain
roots were meant to do.

Caveat on method: slug conventions vary, so counting a root's links to papers by
`fcj-NNN` pattern undercounts issues that use title-only slugs (issue 16 shows 0
links despite 6,469 words). Use each root's own links, not a number pattern.

## P5 — Four editorials missing from the archive

Issues **1, 2, 5 and 23** have no editorial text anywhere in `fcj-static/`. Their
roots are landing pages (701–1,199 words, mostly nav furniture), and the
`/issue-NN-editorial/` page each root links to is absent from disk. Confirmed by
walking every HTML file on those four hosts: the longest pages are all papers,
identified by FCJ numbers in their titles.

Nine further issues (3, 4, 6, 7, 9, 10, 13, 14, plus themed slugs for 15, 16, 17,
19, 20) also link to a missing `/issue-NN-editorial/` page, **but their editorial
prose survives at the issue root**, so only a duplicate is missing. No action.

Mesh has no editorial (764 words at root) — probably by design.

**WRONG — CORRECTED 2026-11-13. The editorials were never missing.** All four
are in `fcj-static/`, and the audit above looked in the wrong place: it walked
the four ISSUE SUBDOMAINS. The editorials are on the **apex host**, where 14 of
them sit as `/issue-NN-editorial/` (issues 1–14), and issue 23's is on its own
host under the themed slug `/issue-23-issues-events-1-digital-networked-media/`.

| issue | source in the mirror | words |
|---|---|---|
| 1 | `fibreculturejournal.org/issue-01-editorial/` | 916 |
| 2 | `fibreculturejournal.org/issue-02-editorial/` | 432 |
| 5 | `fibreculturejournal.org/issue-05-editorial/` | 537 |
| 23 | `twentythree…/issue-23-issues-events-1-digital-networked-media/` | 741 |

All three apex copies were checked against the P3 injection and are clean. Each
is slightly longer than the dump's copy of the same text. **The dump is
therefore off the critical path**, and `build/editorials.py` is not needed:
`tests/test_inventory.py` now asserts all 31 issues have editorial text from the
mirror alone. 27 come from a standalone editorial page, 4 (issues 20, 28, 29,
mesh) from the issue root.

The method error is worth keeping: a per-host walk answers "is it on this host",
not "is it in the archive". The dump route below is still sound, and the probe
still documents the attribution rule — which the mirror-based recovery needed
too, for exactly the same reason.

**Superseded: all four are also recoverable from the dump.** Proved by
`fcjarchive/proofs/editorial-recovery.py`. The dump is a WordPress multisite
dump with 35 per-blog post tables, and each lost editorial sits in the table for
its own issue's blog, with no spam in the recovered text:

| issue | blog table | domain | recovered |
|---|---|---|---|
| 1 | `wp_6_posts` | one | 5,570 B / ~821 words |
| 2 | `wp_7_posts` | two | 3,351 B / ~351 words |
| 5 | `wp_10_posts` | five | 3,225 B / ~455 words |
| 23 | `wp_38_posts` | twentythree | 4,202 B / ~621 words |

Attribution MUST go blog_id -> `wp_blogs`.domain -> issue. Two traps:
- **The blog id is not the issue number** (issue 1 is blog 6), so arithmetic on
  the id is wrong.
- **Slugs cannot be trusted for attribution.** `nineteen…/issue-1-ubiquity` is
  issue 19's editorial under a slug reading as issue 1. Parsing the issue out of
  the slug would misfile editorials.
- Each editorial exists in both the apex blog and its issue blog; the issue-blog
  copy is marginally longer. Pick deterministically, preferring the issue blog.

## Inventory baseline (2026-11-13)

From `inventory.py`, driven from each issue root's own links rather than slug
patterns or the FCJ number sequence — both of which demonstrably miss content.

- **254 pages** linked from the 31 issue roots (213 carrying an FCJ number, 41 not)
- **750 distinct assets referenced, 271 MB**: 508 images (115 MB), 109 PDFs
  (115 MB), 103 ePubs (40 MB)
- **Not referenced by any paper or editorial:** ~1,267 images (41 MB) of theme
  furniture, plus 24 PDFs (108 MB) and 10 ePubs (55 MB) — the full-issue
  compilations on the apex host. **Open decision: do these ship?** Including them
  takes the archive from ~271 MB to ~434 MB.
- **39 unresolved references**, itemised in P5 and P7 above.

Four URL conventions confirmed, sometimes mixed inside one issue: flat files
(`fcj002.html`), extensionless URLs served as `.html` (`/fcj-001`), directory
slugs, and dated permalinks (`/2016/03/21/…`). Any generator must handle all four,
plus percent-encoded UTF-8 and macOS NFC/NFD filename normalization.

## P10 — Supplementary material: some ships, some is genuinely gone

Found by the first generated build, from the 1,004 internal links it rewrote.

**Ships.** FCJ-062 ("Reinventing the Possibilities") links interactive media
under `ten…/wp-content/dynmed/ball_moeller/` — 53 files on disk. The inventory

`dynmed`, `pdfs` and `ePubs` (author content). The generator now adopts any

- FCJ-058 — links `fibreculture.org/issue3_roe.html`, the pre-2008 domain (P6)

These are **neutralised, not hidden**: each keeps its link text and parks the

## P11 — `httpss://`: 1,502 links broken in the database itself

### RESOLVED 2026-11-27 — repaired in `markdown.to_markdown`

330 links in 65 files of `content/` began `httpss://`, so roughly 120 links on
the generated site were dead (`site/papers/fcj-210-…/httpss:/www.youtube.com/…`,
resolved as a relative path). The damage is upstream of the archive: 1,502
occurrences in the 2026-10-22 database dump and 1,386 in the crawled pages. An
http -> https search-and-replace over the database also matched links that were
already https.

It is repaired in the shared converter rather than as a per-page correction
because it is platform damage, not anything an author wrote, and the pattern
cannot match a real URL. `tests/test_markdown.py` `TestDoubledScheme` holds the
archive to zero.

The generated offprints were rendered before the repair; re-run
`build/pdfs.py` so the 65 affected papers' offprints carry the repaired links.
